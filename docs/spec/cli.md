# CLI, interpreter and standalone builds (Level 0)

The first deliverable has two parts:

1. **The `ferro` executable**, built for the host (`cargo build --release -p ferro-cli`).
   It checks and runs Level 0 programs with the reference interpreter.
2. **Standalone binaries**: `ferro bundle` turns a Level 0 program into a single
   native executable for the same OS and architecture as the `ferro` that built it.
   The result runs without FerroBASIC installed and without a JVM.

Both use the interpreter, the semantic reference. Native code generation stays
in M4 ([../roadmap.md](../roadmap.md)). A standalone binary is the `ferro`
runtime plus the embedded program, the same approach as `deno compile`.

## Inputs

`check`, `run` and `bundle` each take one `<input>` from the table below.
`repl` reads submissions from stdin and takes no file argument; `licenses`,
`version` and `help` need no source input. `lsp` exchanges protocol messages over
stdin/stdout and takes no arguments (see [the language server](../language-server.md)).

| Input | Meaning |
| --- | --- |
| `file.bas` | One code module. Two forms are accepted: the module members alone (as in `tests/conformance`), or a B4J module file with its header (lines `Key=Value` up to `@EndOfDesignText@`). A header must have `Type=StaticCode` or no `Type` at all. |
| `project.b4j` | A B4J project. The header is read by `ferro-project`; the main module is the text after `@EndOfDesignText@`. A file whose extension is `.b4j`, in any case, is read as a project. |
| `dir/` | A directory containing exactly one `.b4j`. A directory with none, or with several, is a usage error (exit code 2) that says so. |

Level 0 accepts a `.b4j` only if it is a console project
([project-files.md](project-files.md#at-level-0)):

- `AppType=StandardJava`;
- the only library is jCore;
- there are no other modules (`Module<n>`) and no files (`File<n>`).

Anything else is a compile error (exit code 3) at its header line, naming the
cause, for example:

```text
App.b4j:4:1: error: the project uses library `jfx`: only jCore is supported at Level 0
```

Every such problem is reported, together with the program's other errors.

Source text:

- encoded as UTF-8, with an optional BOM;
- line endings are `\n` or `\r\n` (B4X files use `\r\n`);
- the lossless CST keeps the bytes exactly as read.

## Commands

```text
ferro check  <input>                  parse and type-check, print diagnostics
ferro run    <input> [-- <args>...]   check, then interpret; args go to AppStart
ferro bundle <input> [-o <output>]    check, then write a standalone executable
ferro repl                            start a persistent Level 0 session
ferro lsp                             start the stdio language server
ferro licenses                        print the licence notices
ferro version | help
```

- `ferro help`, and `ferro` with no arguments, print a header and the
  commands. The header is `FerroBASIC <version> (<platform>)`, then the line
  `A multi-target BASIC compiler and interpreter`. `ferro version` prints
  `ferro <version> (<platform>)`.
  - The platform is the one `ferro` was built for, named like the planned
    `--target` values: `<os>-<arch>`, with `x64` and `arm64` for Rust's
    `x86_64` and `aarch64` (`linux-x64`, `macos-arm64`, `windows-x64`).
    Other values keep Rust's `std::env::consts` names.
  - Like every message from `ferro`, they never use the B4X product names.
- `ferro licenses` prints FerroBASIC's licence (`LICENSE`), a blank line,
  then `THIRD-PARTY-NOTICES.txt`: the notices of the third-party code in
  `ferro`, and so in every standalone binary. Both texts are compiled into
  `ferro`. Whoever distributes `ferro` or a standalone binary must include
  them; `bundle` does not write them, `ferro licenses > NOTICES.txt` does.
  The file is generated by `tools/licenses/generate.sh`.
- `run` and `bundle` refuse to continue if `check` reports any error.
- `bundle` writes the interpreter plus the program (see "Standalone binary
  format"); it does not compile:
  - the default output is named after the module or project file, without
    its extension, with `.exe` on Windows. For a directory input that is the
    `.b4j` inside it: `app/` holding `Hello.b4j` gives `app/Hello`. Where the
    output goes depends on the input (see the table below):
    - a module (`.bas`): the current directory, `prices_map.bas` →
      `./prices_map`;
    - a project (a `.b4j`, or a directory holding one): the project file's
      directory, `MyApp/MyApp.b4j` → `MyApp/MyApp`. The IDE names a
      project's directory after the project, so `./MyApp` would be the
      directory itself, and the program belongs with its project anyway.
      The result is the same wherever `ferro` runs from. The directory is
      the one the `.b4j` is named in: a symlinked project file is not
      followed, so its program goes next to the link;
  - `-o` overrides it. Its directory must already exist;
  - an existing output file is replaced, but `bundle` refuses (exit code 2,
    nothing written) an output that is the input file itself or the running
    `ferro`, whether directly, through a symlink or as a hard link, or that
    exists and is not a regular file (a directory, a device such as
    `/dev/null`, a pipe). A directory gets `it is a directory; choose another
    output with -o`: this is what happens, on Linux and macOS, to a project
    named like a directory beside its project file, such as the IDE's `Files`
    or `Objects` (also `files` or `objects` where names ignore case). Any
    other symlink at the output is replaced, not followed;
  - the output gets the executable permission bits on Unix.

  With the project `work/MyApp/MyApp.b4j` and the module
  `work/prices_map.bas` (`MyApp.exe` and `prices_map.exe` on Windows):

  | Run in | Command | Writes |
  | --- | --- | --- |
  | `work/` | `ferro bundle MyApp` | `work/MyApp/MyApp` |
  | `work/` | `ferro bundle MyApp/MyApp.b4j` | `work/MyApp/MyApp` |
  | `work/MyApp/` | `ferro bundle .` or `ferro bundle MyApp.b4j` | `work/MyApp/MyApp` |
  | `work/` | `ferro bundle prices_map.bas` | `work/prices_map` |
  | `work/MyApp/` | `ferro bundle ../prices_map.bas` | `work/MyApp/prices_map` |
  | `work/` | `ferro bundle MyApp -o build/app` | `work/build/app`; `work/build/` must exist |
- In 0.0.1 this command was called `build`; `build` now has the meaning below.
- Arguments are bytes, not necessarily UTF-8. File names may contain any
  bytes. Arguments passed to `AppStart`, by `run` or by a standalone binary,
  are decoded as UTF-8 with undecodable bytes replaced by U+FFFD, as the JVM
  does.
- Output that cannot be written (stdout or stderr closed, or a pipe whose
  reader has gone, as in `ferro help | head -1`) is dropped silently: it
  never crashes `ferro` or changes its exit code.
- `ferro-difftest` drives the conformance tests and prints the compatibility
  report ([../compatibility-testing.md](../compatibility-testing.md#the-report)).

### Interactive REPL

`ferro repl` starts a Level 0 session; it takes no file argument. See the
[REPL tutorial](../tutorial.md#9-the-interactive-repl). Statements execute once; bare expressions
print with Log's conversions. Assignment wins (`n = 3` assigns, `(n = 3)`
compares). Calls returning values print once; void calls add no output.
Statements, complete Subs, Type declarations, multiline blocks and strings
are accepted. An incomplete construct gets a continuation prompt, not an
error, until EOF or invalid syntax. Blank lines do not finish a block.

Session variables are module globals. Values, aliases, collections, random
state and LastException survive submissions. Types are fixed; a same-type
Dim resets its value normally. Constants cannot be redefined. Types cannot
be redeclared; reset to change their layout. A Sub can be replaced with the
same parameter count/types and return type; dependent Subs are rechecked.
New declarations that would change a previously checked Sub's local bindings
are refused; choose another name. Definitions are submitted one at a time. Type declarations must be standalone
submissions, not nested in blocks or Subs.
Failed compilation leaves the session unchanged. Compilation commits the
submission's declarations before execution; an uncaught runtime error keeps
completed mutations and those declarations, unwinds execution and allows
another interactive submission.

Interactive prompts (`> ` and `... `) and terminal editing/echo go to stderr;
program output and expression results go to stdout. FerroBASIC supplies line
editing and in-memory history when stdin and stderr are terminals and TERM is
supported. Unix requires a nonempty TERM; Windows also accepts an unset TERM.
`dumb`, `unknown` and `emacs` (case insensitive) use the plain reader. Redirecting
stdout alone still allows editing; redirecting stderr disables editing and
history. The plain reader retains prompts and interactive error recovery when
stdin is a terminal, without FerroBASIC echo or escape sequences. Piped stdin
always uses the plain reader, without prompts or history processing, regardless
of the output destinations.

In editing mode, Left/Right and Home/End move the cursor; Backspace/Delete and
ordinary typing edit input. Up/Down move within multiline input and recall
previous/next submissions at the first/last line. Recalled input is editable;
recall never executes it. Enter submits a syntactically complete submission or
adds a continuation line when the parser says it is incomplete. Blank lines
never finish incomplete blocks. A recalled multiline Sub or block is one
editable buffer and Enter submits it as a whole, from any cursor position.
There is no completion, syntax highlighting or persistent history.

History retains the latest 100 nonblank BASIC submissions for this REPL process
only, including submissions with compilation/runtime errors so they can be
corrected. It preserves source whitespace and internal newlines, removes only
the final input newline, and suppresses consecutive exact duplicates. Older
duplicates remain. Control lines, cancelled pending input and incomplete EOF
input are not saved. No history file is read or written. `:reset` keeps recall
history: runtime session state and input history are independent. On exit all
history is discarded. During an incomplete block, recalled input is appended to
any input already accepted before a control line such as `:help`; use `:cancel`
to discard pending input before recalling an unrelated submission.

Ctrl+C terminates the process, including while BASIC executes; recoverable
execution cancellation is deferred. In editing mode it exits 130 after terminal
cleanup at a prompt; during execution the ordinary OS termination applies.
Raw mode is left before execution. `:help`, `:quit`, `:reset` and `:cancel`
are control lines outside string literals. Cancel discards pending input;
reset clears pending input, definitions and runtime state, keeping history.
In editing mode Ctrl+D deletes forward in nonempty input and signals EOF on an
empty buffer, including an empty continuation after `:help`. To send EOF while
preserving incomplete editable input for diagnosis, use Ctrl+Alt+D (or Esc then
Ctrl+D where the terminal encodes Alt that way). Windows Ctrl+Z also signals
explicit EOF; plain Windows console input uses Ctrl+Z followed by Enter.
On Unix, Ctrl+Z in editing mode is Emacs undo, not shell job suspension. The
plain reader retains the terminal's Ctrl+Z suspension behavior. Ctrl+C still
terminates in either mode. Explicit EOF finalizes the displayed input before
printing diagnostics or returning to the shell.
Normal EOF or quit exits 0; incomplete EOF exits 3. Piped input has no prompts and stops
on the first error: 3 for compilation, 1 for runtime. Bad arguments and
input-read failures exit 2. ExitApplication/ExitApplication2 terminate the
session with the ordinary exit status. Explicit AppStart, Process_Globals,
project headers and project-only directives are refused in a session.
Compact diagnostics identify the entered submission (`<repl:N>:line:column`),
including errors in previously defined Subs. The session does not execute previous input again.

Terminal modes and stdout routing are restored on normal exit and handled input
errors. A terminal that advertises support but cannot answer cursor-position
queries produces an input-read error (exit 2) after cleanup; set `TERM=dumb`
to select the plain reader. Unhandled external termination cannot guarantee
cleanup. The editor runs only in the serial CLI input phase, never concurrently
with BASIC execution.

The [terminal library decision](../research/repl-line-editing.md) records the
adapter design and dependency tradeoffs.

#### Deferred REPL improvements

These are proposals with no assigned milestone or schedule:

- A session command to load commands or source from a file. Piping input into
  `ferro repl` already works, but does not load a file into an existing session.
- Recoverable interruption of executing BASIC code, returning to a usable
  prompt. Ctrl+C currently terminates the process. `:cancel` only discards
  pending input; it cannot interrupt code that is executing.

### Planned commands

These names are reserved. Until a command is implemented it exits with code 2
and a message saying what is missing and when it arrives, and it never does
something else instead (`ferro build` on a module points to `ferro bundle`).

| Command | Meaning | Arrives with |
| --- | --- | --- |
| `ferro compile <input> [--target <t>] [--emit <kind>] [-o <output>]` | compile one module or project for this machine (no `--target`) or for another target | JVM backend (M3), native and WebAssembly (M4), microcontrollers (M5) |
| `ferro targets` | list the targets and what each needs installed | `compile` |
| `ferro build [<project>]` | build a project from its project file: compile for the project's default target, then package the result where the target needs it | JVM backend (M3) |
| `ferro test`, `ferro fmt` | conformance runner, formatter | M1 and later |

Decisions behind them:

- **One verb for every target.** Generating source (Java, JavaScript) is
  compiling too, so there is no separate `transpile`: the target says where
  the program runs, `--emit` chooses the form of the output when a target has
  more than one (`exe`, `obj`, `asm`, `llvm-ir`, `class`, `java`, …).
- **Targets** have short names, and full LLVM target triples are accepted
  too (`x86_64-unknown-linux-gnu`), so new architectures are new names, not
  new commands. Planned, by milestone:
  - M3: `jvm` (bytecode by default; Java source with `--emit java`) and
    `android`;
  - M4: native desktop (`linux-x64`, `linux-arm64`, `windows-x64`,
    `windows-arm64`, `macos-x64`, `macos-arm64`) and `wasm`;
  - M5: microcontrollers, `pico` (Raspberry Pi Pico) first, then Arduino
    boards and others;
  - later: `ios-arm64`, `js`. *(open: names, and whether `js` is its own
    backend or goes through `wasm`.)*
- **`build` works on projects.** With no argument it uses the project file in
  the current directory. The default target follows the project type:
  `.b4j` → JVM, `.b4a` → Android, `.b4i` → iOS, `.b4r` → microcontroller;
  `--target` will override it. `ferro run` already accepts the Level 0 B4J
  console projects described under "Inputs".
- **Packaging** (an `.apk` or `.aab`, an `.ipa`, a macOS `.app`, installers)
  is part of `build`. The word is kept free for it, which is why the
  interpreter bundle is `bundle` and not `package`.
- **A new text project format** (a `ferro.toml`, with dependencies) may come
  later, as an addition only: a B4X project must always build unchanged from
  its own project files, never needing the new format. *(open: format and
  timing.)*

## Exit codes

| Code | `ferro check` / `run` / `bundle` / `repl` | Standalone binary |
| --- | --- | --- |
| 0 | success / program ended normally | program ended normally |
| *n* | `run` / `repl`: the program called `ExitApplication2(n)` | the program called `ExitApplication2(n)` |
| 1 | `run` / piped `repl`: uncaught runtime error | uncaught runtime error |
| 2 | usage error, a planned command that is not implemented yet, unreadable input, REPL input-read failure, cannot write bundle output | corrupt embedded payload |
| 3 | compile errors; `repl`: piped compilation error or incomplete EOF | — |

Interactive REPL errors normally recover within the session; see
[Interactive REPL](#interactive-repl). Program exit statuses keep their low
8 bits. Exit code 1 for an uncaught B4J error is recorded by
[`uncaught_error`](../../tests/conformance/level0/uncaught_error.meta.toml).

## Diagnostics

Compile errors go to stderr, one per problem, as
`path:line:column: error: message`, followed by the source line and a caret.

- Lines and columns start at 1. Columns count characters (Unicode scalar
  values); the byte order mark that may start a file is not counted.
- At most 100 errors are printed for a file. Then `... and N more error(s) not
  shown`, and the last line is always the total, `N error(s)`.
Warnings use `warning:` and do not fail the command. Messages never use the
B4X product name. Each says what is missing and at which level or target
it arrives.

## Runtime errors

- A runtime error has a **kind**, named after the Java exception B4J would raise:
  - `java.lang.RuntimeException`, e.g. an uninitialised `List`/`Map`;
  - `java.lang.NumberFormatException`;
  - `java.lang.IndexOutOfBoundsException`;
  - `java.lang.StringIndexOutOfBoundsException`;
  - `java.lang.ArithmeticException`;
  - `java.lang.ClassCastException`;
  - `java.lang.UnsupportedOperationException`;
  - `java.lang.ArrayIndexOutOfBoundsException`;
  - `java.lang.ArrayStoreException`;
  - `java.lang.NullPointerException`;
  - `java.util.ConcurrentModificationException`;
  - `java.lang.StackOverflowError` and `java.lang.OutOfMemoryError`, which
    `Try` does not catch.

  The kind is what `ferro-difftest` compares. Messages are compared only where
  [level0-builtins.md](level0-builtins.md) quotes them exactly.
- An uncaught error prints to stderr, in the shape B4J uses:

  ```text
  Error occurred on line: <line> (<module>)
  <kind>: <message>
  ```

  It then exits with code 1. stdout produced before the error is kept and flushed.

## Interpreter

- Pipeline:
  - `ferro-syntax` builds the lossless CST;
  - `ferro-hir` resolves names, hoists locals, infers and checks types, and
    marks implicit conversions;
  - `ferro-mir` lowers to the typed MIR: explicit `Convert(from, to)`, no
    `For Each`, no smart strings;
  - `ferro-interp` executes the MIR.
- Values are tagged: `Boolean`, `Byte`, `Short`, `Int`, `Long`, `Float`,
  `Double`, `Char`, `String`, `Null`, and references to `List`, `Map`, arrays
  and `Type` records.
  - A boxed `Object` keeps its runtime tag.
  - Strings must behave as UTF-16 (`Length`, `CharAt`, `SubString` indices);
    the internal representation is free.
- Integer arithmetic wraps like Java. Floating point is IEEE 754 binary64 or
  binary32, with no fused or extended precision.
- `Log` writes through a buffered stdout that is flushed at exit, at
  `ExitApplication`, and before a runtime error is printed.
- Recursion depth is limited. Overflowing it is a runtime error of kind
  `java.lang.StackOverflowError`, not a crash of `ferro`. So is comparing
  (`=`, `IndexOf`) collections nested more than 3000 deep, or printing
  collections and records nested more than 7000 deep, where Java's `equals`
  and `toString` recurse too (deviation D2: Java's limit depends on its
  stack).
- Data may nest to any depth: a linked list of 100,000 records is freed
  without recursion.
- Memory is limited. When an allocation fails, or a String or
  `StringBuilder` would be longer than Java's limit of 2,147,483,647 UTF-16
  code units, the program stops with `java.lang.OutOfMemoryError: Java heap
  space`, keeping the output printed so far. Arrays hold at most 2^28
  elements.

## Standalone binary format

`ferro bundle` embeds a **package** in a copy of the running `ferro`
executable. The package is a payload followed by a trailer:

```text
package = [ payload ][ payload length: u64 LE ][ magic: "FERROBASIC\0PKG" ][ format version: u16 LE ]
```

On Linux and Windows the package is appended to the executable. On macOS it
is embedded with `libsui` instead (see below).

- The **payload** is the checked program as source text. It is the input module,
  or the project header plus main module, as UTF-8 bytes in a small container:
  - an entry count (u32 LE), then each entry as its name and its bytes, each
    a length (u32 LE) followed by the data; names are UTF-8;
  - format version 1 has one entry, `main.bas`, the module's source as read.
  - A payload with trailing bytes, a truncated entry or no `main.bas` is
    corrupt (exit code 2).

  Source rather than MIR keeps the format free of any IR serialisation. The
  program was already fully checked at build time, so re-parsing at start-up
  cannot fail on a well-formed payload.
- **At start-up** `ferro` looks for a package in its own executable: at the
  end of its file (`std::env::current_exe`), or on macOS through `libsui`.
  - If the trailer is present, it runs the embedded program: every
    command-line argument goes to `AppStart`, and `ferro`'s own CLI is not
    parsed.
  - If the trailer is absent, it behaves as the normal CLI.
  - A trailer whose version it does not know, or whose length is impossible,
    exits with code 2.
  - So does an executable that cannot locate or read its own file: it never
    falls back to the CLI in place of its program.
- Linux (ELF) and Windows (PE) ignore appended bytes, so the result runs as is.
  Verified on Linux x86_64 and Windows x64.
- **macOS**: `codesign` rejects a Mach-O file with bytes after its last
  segment ("main executable failed strict validation"), and Apple Silicon
  refuses to run unsigned binaries. So the package is embedded with
  [`libsui`](https://github.com/denoland/sui), the library `deno compile`
  uses (MIT):
  - **Apple Silicon**: the package goes in a new Mach-O section
    (`__SUI,__ferro`) before `__LINKEDIT`, and `libsui` signs the result ad
    hoc itself.
  - **Intel**: `libsui` appends the package after its own marker and extends
    `__LINKEDIT` to cover it. `ferro bundle` then signs ad hoc with
    `codesign --force --sign -`, and reports an error if that fails.
    `libsui` stages a copy at `$TMPDIR/sui_tmp_<pid>` with a call that
    follows symlinks, so `ferro bundle` creates that path first, exclusively;
    if it already exists, the build stops with an error.
  - At start-up `libsui` finds the package again: through `getsectdata` on
    Apple Silicon, by scanning the file for its marker on Intel.
  - The output must pass `codesign --verify --strict` (a test checks this
    on macOS). Verified on an Apple Silicon Mac: native arm64, with
    `cargo test --workspace` passing, and x86_64 through Rosetta. CI also
    exercises x86_64 on Intel macOS.
- **Writing the output**: the binary is staged in a new, uniquely named file
  next to the output (never an existing file or a symlink), signed there on
  Intel Macs, then renamed over the output. If any step fails, an existing output
  is left untouched and the staged file is removed.
- **Dependencies**: the output depends on exactly what `ferro` itself depends on.
  On Linux that is the system C library (glibc), unless `ferro` was built for
  `*-linux-musl`, which makes the output fully static (verified with
  `x86_64-unknown-linux-musl`). On Windows it needs no
  extra DLLs.
- Building for another OS or architecture is out of scope here (see M4 and the
  `zig cc` / `cargo-zigbuild` question).

## Acceptance criteria

The first implementation is done when, on Linux x86_64 and in CI:

1. Every `tests/conformance/level0/*.bas`, negative tests included, parses
   into a CST that prints back byte-identical.
2. `ferro check` passes on every test that FerroBASIC accepts according to
   its metadata (`negative` and `ferro_rejects` tests are refused).
3. The negative and `ferro_rejects` tests are rejected by `ferro check` with exit code 3.
4. `ferro run` on every test that has an `.expected` file or, while none is
   recorded, a `.provisional` file produces identical stdout, and the uncaught
   error named in `uncaught_error` when there is one
   (see [../compatibility-testing.md](../compatibility-testing.md#test-file-layout)).
   Pending tests with neither file have no stdout expectation; their acceptance
   and ending are checked. Deviation tests follow their documented contract
   instead of comparing reference stdout. Currently no tests are pending or
   provisional; `precedence_and_or` has a recording.
5. For every test in point 4, `ferro bundle` produces a binary whose stdout and
   exit code are identical to `ferro run`'s. The binary must also keep working
   after the build tree and `ferro` itself are removed.
6. The required checks in `scripts/check-all.sh` pass. FerroBASIC workspace
   crates deny unsafe code through the workspace lints.
