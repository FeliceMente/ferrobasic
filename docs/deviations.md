# Deviations from B4X

Every known, accepted difference between FerroBASIC and the original B4X
toolchain. Each entry needs a conformance test with `status = "deviation"`.

| ID | Area | Target(s) | Original behaviour | FerroBASIC behaviour | Reason | Test |
| --- | --- | --- | --- | --- | --- | --- |
| D1 | Syntax | all | Nesting depth is limited only by javac, whose limit is unknown (open question); B4J 10.70 builds 1100 levels (recorded) | Statements and expressions nested more than 1000 levels deep in a Sub (operator and member chains count one level per operator), or smart strings nested more than 100 deep, are a compile error | Every stage walks the tree recursively; an unbounded depth crashed `ferro` with a stack overflow and made parsing quadratic | `tests/conformance/level0/deep_nesting`; `crates/syntax/src/tests.rs` (`nesting_*`), `crates/cli/tests/safety.rs` (`deep_*`) |
| D2 | Runtime | all | Memory is limited by the JVM heap; an `Int` array element takes 4 bytes, and arrays may hold up to about 2^31 elements; how deep `equals` and `toString` may recurse into nested collections before `StackOverflowError` depends on the JVM's stack (on the recording machine, comparing works at 2000 levels and overflows by 5000, printing works at 5000 and overflows by 10000) | Every array element takes 16 bytes on 64-bit platforms, whatever its type, and a new array holds at most 2^28 elements (counting, for a rank above 1, its rows as well); running out raises `java.lang.OutOfMemoryError` as in Java; comparing deeper than 3000 levels and printing deeper than 7000 raise `java.lang.StackOverflowError`, whatever the stack | One value representation for every slot keeps the reference interpreter simple; typed storage can come with the compiled backends; the interpreter walks nested data without recursing, so its limits are fixed numbers chosen inside the recorded ranges | `crates/cli/tests/safety.rs` (`running_out_of_memory_is_a_java_error`); `tests/conformance/level0/deep_equals`, `deep_printing` |
| D3 | Runtime | all | `NumberFormat` (and `NumberFormat2`) take a double's digits from the JDK's older `FloatingDecimal` conversion, which for subnormals and for a few other values (3 in 100,000 random doubles, all above 2^63) gives 16 or 17 digits where fewer round-trip: with no fraction digits, the double 28551757570297602048 (`2.85517575702976E19`) formats as `28,551,757,570,297,602,000` | The shortest digits, as `Double.toString` gives them: `28,551,757,570,297,600,000`. Its other differences from `Double.toString` (integers from 2^53 to 2^63, powers of two) are reproduced | Reproducing it would mean re-deriving that algorithm's digit generation from its behaviour alone; the difference is in the 16th and 17th significant digits | `tests/conformance/level0/number_format_d3` (its reference output is recorded from B4J 10.70); `crates/interp/src/number.rs` (`number_format_*` tests) |
| D4 | Runtime | all | `SortType` / `SortTypeCaseInsensitive` raise, wrapped in a `RuntimeException`, the problem of the first pair that `Collections.sort` (`TimSort`) compares, an order that depends on the values: for `[A(1), A("x"), B(1)]` (records with an `Object` field `N`) the cause is `ClassCastException`, from comparing the second item with the first (a `Catch` sees the cause itself in `LastException`) | The problem of the first item in list order, after reading every item's field: an item of another type (`IllegalArgumentException`) before field values that do not compare (`ClassCastException`), so the cause above is `IllegalArgumentException`. The `RuntimeException`, and the cause in a list with one kind of problem, are as in B4J; the list's order after the error is D5 | Reproducing it would mean reproducing `TimSort`'s comparison order; the difference is only in which cause a list with several different problems reports, and its text is JDK wording | `tests/conformance/level0/sort_type_order_d4`; `crates/interp/tests/sort_type.rs` |
| D5 | Runtime | all | A `Sort`, `SortCaseInsensitive`, `SortType` or `SortTypeCaseInsensitive` that raises leaves the list partly sorted: `TimSort` sorts it in place and stops at the first comparison that fails, so `[1, 3, 2, "x"]` is `[1, 2, 3, x]` after `Sort` raises `ClassCastException` | The list is left as it was: `[1, 3, 2, x]` | FerroBASIC checks every item before it sorts; reproducing the partial state would mean reproducing `TimSort`'s comparison order. Only a program that catches the error and then reads the list sees the difference | `tests/conformance/level0/sort_partial_d5` (its reference output is recorded from B4J 10.70) |
